**Дата:** 23.10.2026. **Статус:** ✅ проектирование завершено; ⬜ реализация не начиналась.
**Границы:** изменения допускаются только в документации. Живые n8n, SQL, Supabase, сервер, файлы, задания и расписания не изменены. Пятиминутный Trigger в рабочем n8n по последнему отчёту пользователя выключен; в обезличенном GitHub JSON `disabled` не указан, поэтому это НЕ подтверждение настройки живого экземпляра.

Источники: `PLAN.md`, `docs/07_KB_RETRY_AND_CANCEL_DESIGN.md`, `docs/08_SESSION_HANDOFF.md`, `DB_WORKFLOW_CONTRACT.md`, `workflows/current/Катона — Служебный Telegram и база знаний — ЗАКРЫТЫЙ ТЕСТ.json` (108 узлов; репозиторный обезличенный снимок, не гарантированно идентичен живому n8n). Реальные определения функций и настройки retention на сервере **в этой задаче не проверялись**. Никаких выводов о первоначальной технической причине зависшего worker не сделано.

## 1. Проверенная схема сегодня

1. Вход: `Принять вход служебного бота` → `Служебный_Сохранить служебный вход` → `KB-01A Проверить источник документа` → `Служебный_KB-01A Скачать Markdown` → `KB-01A Проверить фактический файл`.
2. `KB-01A Проверить фактический файл` превращает бинарное содержимое в `kb01a_base64` внутри JSON. `Служебный_KB_Зарегистрировать загрузку` передаёт его через `decode($2::text,'base64')` в `katona.zaregistrirovat_zagruzku_znaniy`. По предыдущему аудиту `katona.zagruzki_znaniy.ishodnyy_fayl` — `bytea NOT NULL`. Значит, даже терминальная отметка ошибки не удаляет исходные bytes.
3. `KB-01A Сформировать результат регистрации` отправляет Telegram только сообщение о **долговечной регистрации**, не об успешной публикации. `KB-01A Запустить обработку знаний?` сразу запускает `KB-03B1 Настройки worker` также для `dublikat` с `zadanie_id`. Отдельный `Проверять очередь знаний каждые 5 минут` ведёт к тому же worker; в репозиторном снимке у узла нет `disabled=true`, но пользователь сообщил об отключении и публикации этого изменения в **живом** n8n.
4. Worker получает задание из `katona.zabrat_zadanie_znaniy` с арендой 900 секунд; разбирает Markdown, формирует фрагменты/вопросы, вызывает два API embeddings, сохраняет черновые данные и вызывает `katona.opublikovat_versiyu_znaniy`.
5. В репозиторном JSON `retryOnFail=true, maxTries=2` задано в `KB-03A OpenAI embeddings`, `KB-03B1 OpenAI embeddings вопросов` и `Служебный_KB_Опубликовать версию`. Это автоматические повторные вызовы, помимо повтора заданий на уровне БД.
6. В статус `povtor` с запуском через примерно 300 секунд возвращают как минимум: `Служебный_KB_Вернуть после ошибки проверки`, `...ошибки профиля`, `...после B2`, `...ошибки структуры`, `...ошибки A2`, `...ошибки B`, `...после 03A`, `...ошибки 03A`, `...после 03B`, `...ошибки 03B`. Публикационная ветка `...Завершить после ошибки публикации` использует `povtor` по умолчанию. Это **несовместимо** с правилом «одна попытка».
7. `KB-03C1 Проверить результат публикации` для неуспеха допускает `povtor`. Публикация может быть **неизвестной** после сетевого разрыва: повтор SQL-вызова публикации без сверки результата опасен. Ноды возврата job и `KB-03C1 Итог публикации` не подключены к самостоятельному итоговому Telegram-уведомлению.
8. По read-only проверкам от 23.10 две TEST-загрузки имели `v_rabote` с истёкшей арендой и `povtor` после 3 попыток; логическая блокировка подтверждена. По отдельному разрешению пользователь закрыл обе записи транзакцией `KAT-KB-CANCEL-01 VERIFIED`; исходные bytes не удалены, активная версия не создана. Первопричина обрыва первого выполнения **не установлена**. Из описания исходного шаблона известен риск `dokument_zanyat`, если занятость определяется по `v_rabote` без проверки срока аренды; соответствие живой функции Катоны пока не доказано.

## 2. Целевая архитектура (рекомендуемая)

**Выбранный путь: однократная обработка в рамках одного запуска ветки KB без постоянной записи исходного файла.** Другая функциональность служебного бота остаётся нетронутой.

```text
Telegram update
  → разрешённый отправитель + лимит размера + дедупликация update_id
  → регистрация ТОЛЬКО метаданных попытки в Supabase
  → временное чтение binary в одной n8n execution
  → валидация Markdown → фрагменты → embeddings (каждый API-вызов 1 раз)
  → проверка качества → атомарная публикация при подтверждённом результате
  → терминальный итог операции + отдельная заявка на Telegram-уведомление
  → Telegram: опубликовано / конкретная ошибка / исход неизвестен
  → удалить все временные bytes и неопубликованное содержимое
```

- **Supabase:** отдельный минимальный журнал попыток: ID Telegram update и загрузки, отправитель/чат с ограниченным доступом, имя файла без опасных символов, безопасный hash, время, состояние, код ошибки, `version_id` при успехе. Отдельный журнал/очередь уведомлений хранит `attempt_id`, адресата, код сообщения, `delivery_status`. Ни один из журналов **не хранит** исходный файл, base64, содержимое Markdown, большие ошибки или embeddings.
- **Временные данные:** бинарный файл нужен только пока идёт текущее выполнение; убрать `kb01a_base64` из JSON и не передавать `decode(...base64)` в регистрацию. Не записывать исходный файл в `zagruzki_znaniy` либо другую постоянную таблицу. Изменения старой таблицы/функций проектировать **только после чтения** текущих FK, CHECK, триггеров, обязательных полей и тел функций. Возможна новая совместимая ветка функций/таблиц без разрушения существующей.
- **После неуспеха:** очищать также **неопубликованные текстовые фрагменты, вопросы, векторы и временные версии** данной попытки, сохраняя лишь статус/код/время. Нельзя удалять действующую опубликованную версию или чужие документы. Успех хранит только нужное опубликованное знание; оригинал не требуется сохранять.
- **n8n:** отключить сохранение входного binary, промежуточных JSON и полных execution outputs в постоянной истории в границах, которые допускает установленная версия n8n; проверить фактический `binaryMode: separate`, execution retention, очередь/воркеры, pin-data, ошибки, файловые каталоги, резервные копии и логи. Отключение одной настройки не доказывает физическую очистку. Для аварийных остановок нужен измеримый срок очистки и проверяемый механизм удаления временных данных.
- **Сохранение возможности диагностики:** допустимы короткий код ошибки, ID попытки и время; содержимое, токены и полные stack trace в Telegram и журналах не писать. Исторические TEST bytes не удалять без отдельного согласования.
- **Ограничение:** нельзя гарантировать удаление уже хранящихся копий у Telegram, провайдера, в старых backup или журналах без отдельной политики и аудита.

## 3. Контракт одной попытки

- **Приём:** уникальный ключ `(kompaniya, bot, telegram_update_id)`; дубли одного события дают прежний статус без новой обработки. Новая ручная отправка пользователем — **новая** попытка, даже если файл/логический документ тот же. Только `accepted` может атомарно перейти в `running` ровно один раз. Никаких веток `povtor` и повторного claim.
- **Состояния:** `accepted` → `running` → `published | failed | unknown`; `cancelled` — отдельный защищённый случай (KAT-KB-RETRY-01C). Терминальные `published`, `failed` и `cancelled` не возвращаются в обработку. `unknown` означает запрет на повтор исполнения при необходимости **read-only сверки**, не подтверждённую неудачу.
- **Блокировка/аренда:** выдавать однократный токен владения `nomer_vladeniya`, срок завершения, статус конкретной версии; все write/publish завершаются только при совпадении токена и разрешённого состояния. При истечении срока **никто не запускает обработку снова**. Отдельная проверка состояния помечает `unknown` и уведомляет; если документ реально опубликован — фиксирует успех без нового publish. Занятость логического документа должна учитывать устаревшую аренду, не оставляя бесконечный `dokument_zanyat`; конкурирующая загрузка получает понятный итог, а не retry.
- **Каждый шаг:** ошибка парсинга, структуры, embeddings, поиска, БД, истёкший deadline — немедленное прекращение данной попытки, конечный код ошибки/статус при доступности БД, очистка временного контента и создание уведомления. OpenAI 429/5xx не перезапускают embeddings; `retryOnFail` и скрытые повторные вызовы отключить. Для SQL publish при обрыве **не выполнять второй publish**, даже если клиент не получил ответ.
- **Публикация:** одна защищённая транзакция проверяет актуальный `attempt_id`, токен владения, готовность проверок, текущий active pointer и ожидаемый active pointer; публикует ровно нужную версию и фиксирует завершение. Клиентский RAG видит только `opublikovana` через active pointer, не черновики.
- **Неизвестный исход:** после timeout/обрыва публикации сохранить `unknown` (если возможно) и выполнить только **read-only сверку** по attempt/version/active/status. При невозможности сверки Telegram получает «Статус публикации пока не подтверждён, требуется проверка», не «не опубликовано». Оператор сверяет и закрывает без повторной обработки.
- **Уведомление:** отдельное действие после установления результата, сообщение отправителю служебного бота в личный чат. `accepted` означает лишь «Файл получен, проверяется». Финальное сообщение: «Опубликован: <имя>, версия N», либо «Не опубликован: <причина>. <что сделать>», либо «Исход пока не подтверждён; проверяем». Ошибки Telegram отделены от обработки KB: разрешён повтор **доставки сообщения**, но не embeddings/публикации; возможны дубли Telegram-сообщений, их нельзя обещать исключить полностью.
- **Отказ Supabase до регистрации / Telegram до получения файла:** по возможности одно безопасное Telegram-уведомление напрямую, без сохранения bytes; если Telegram тоже недоступен — технически невозможно гарантировать немедленное сообщение. Для crash/hang после приёма предусмотреть только контроль метаданных и очистку, **не запуск всего worker**. Старый пятиминутный Trigger не использовать.

## 4. Причины зависаний и что подтвердить до кода

| Риск | Уже видно | Что проверить перед реализацией |
| --- | --- | --- |
| Возврат `povtor` и запуск duplicate | Множество SQL-веток, `KB-01A Запустить обработку знаний?` | Ответы функций, текущие проверки состояния, идемпотентность update_id |
| Длинная обработка / истечение аренды | В конфиге 900 сек, live был истёкший lease | Живые n8n Execution/error и SQL lease+fencing, безопасные deadline |
| Конкуренция по логическому документу | В TEST было `dokument_zanyat` | `pg_get_functiondef` **в схеме katona**, особенно условия `v_rabote` |
| Тихая остановка на PostgreSQL/OpenAI | Отдельные узлы `continueOnFail`, не все ошибки имеют общий итог | Обработка errors/missing output каждой ветки, timeout, аварийный handler |
| Неизвестный исход publish | `retryOnFail=true` на публикации | Атомарная функция, проверка active/version, запрет повторного publish |
| Долговечные данные ошибки | `bytea NOT NULL`, base64 в JSON, `binaryMode=separate` | Реальная политика n8n/Supabase backups, исторические черновики и fragments |

До выполнения следующего этапа запросить **только чтение** по фактическим таблицам `zagruzki_znaniy`, `zadaniya_znaniy`, `dokumenty_znaniy`, `versii_znaniy`, `fragmenty_znaniy`, вопросам/проверкам, индексам/FK/CHECK/триггерам/ролям и функциям `zaregistrirovat_zagruzku_znaniy`, `zabrat_zadanie_znaniy`, `zavershit_zadanie_znaniy`, `podgotovit_versiyu_znaniy`, `sohranit_fragmenty_znaniy`, `sohranit_kontrolnye_voprosy`, `sohranit_proverki_znaniy`, `opublikovat_versiyu_znaniy` (и их вызовам). Никакой `UPDATE`/`DELETE` на этой диагностике.

**Меры при внедрении:** сохранять снимки текущего JSON и определения функций, тестировать в закрытом контуре и с отдельным контрольным документом, переключать только KB-ветки при разрешении; остальные служебные действия и клиентский Workflow не менять. Rollback — вернуть старый путь **только с запретом его автоматических retry до отдельного решения**, чтобы откат не восстановил прежний цикл. Никаких автоматически запускаемых DELETE/cleanup до согласования политики старых данных.

## 6. Таблица будущих тестов (ожидаемый результат)

| Сценарий | Обработка | Telegram | Данные |
| --- | --- | --- | --- |
| Корректный Markdown + проверки OK | 1 раз; publish 1 раз | Подтверждённая версия | Только активное проверенное знание |

**Стоп-условия:** если SQL-функции не защищают старую активную версию; если нельзя обеспечить очистку исходника/черновика; если n8n продолжает долговечно сохранять содержимое; если `unknown` может вызвать новый publish; если тест требует включить прежний пятиминутный Trigger — не переходить к активации.

**Текущая задача по команде пользователя:** `KAT-KB-RETRY-01B2` — см. [чек-лист](10_KB_RETRY_01B2_READ_ONLY_AUDIT.md). SQL и настройки живой системы в этом документе не менялись. Только после результатов B2 возможен точный SQL/JSON проект; реализация **сейчас запрещена**.
