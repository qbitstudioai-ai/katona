## Решение Павла (обязательное для будущей архитектуры)
- На одну пользовательскую загрузку — **одна попытка обработки**; автоматического повторного запуска обработки после ошибок Markdown, векторизации, сети или БД быть не должно.
- Telegram должен сообщать понятную причину отказа и что исправить. Следующую попытку пользователь инициирует сам новым сообщением/файлом.
- Неудачный исходный файл не должен оставаться **на постоянном хранении** в n8n/Supabase. Для корректной реализации нужны временная зона обработки, стратегия удаления, проверка n8n execution/binary retention, логов и резервных копий.
- Минимальный след операции (ID, итог, код ошибки, время) нужен для защиты от дублей и аудита; не путать с сохранением содержимого файла.
- При неизвестном результате публикации нельзя ложно утверждать, что публикации не было; сначала выяснить итог. Уведомления Telegram и публикация отдельно.
- До внедрения и проверки нового контракта не включать пятиминутный Schedule Trigger. Новые файлы через Telegram всё ещё могут запускать worker по входящему пути.
