## Примечание: диагностика Executions важна (24.10.2026)

После просмотра настроек пользователь отметил, что полное отключение истории лишит нас возможности нормально исследовать ноды при сбоях. Это верно: n8n позволяет отдельно сохранять успешные, ошибочные и ручные execution; сохранённые данные служат материалом для Debug. Поэтому инструкция выше «отключить всё немедленно» **пересматривается, не считать согласованной**.

**Временное предложение для закрытых тестов строго на искусственном Markdown без секретов:** `Save` для failed/successful/manual, `Do not save` для progress; заранее выбрать короткую политику очистки и после теста проверить удаление записей. До исправления retention и разрешения тестов ничего не запускать. **Для эксплуатации:** KB-путь должен писать только безопасные метаданные ошибок, не исходный Markdown/binary, а хранение менеджерских execution настраивать отдельно. Если всё остаётся одним Workflow, настройки применяются ко всему Workflow, поэтому разделение KB и менеджерских путей требует проектного решения. Никакие изменения UI не производились ассистентом.

Дополнительный риск: обычный Telegram доставляет webhook с заголовком `X-Telegram-Bot-Api-Secret-Token` только при настроенном `secret_token`; текущий `Header Auth` может требовать иной заголовок. Перед тестовой отправкой сообщений нужно проверить их соответствие, не выводя значение токена.


## Пользователь подтвердил один включённый Workflow; URL-маршруты требуют исправления (24.10.2026)

В n8n **только один служебный Workflow B4; он включён**. Ранее экспорт был `active=false`, поэтому состояние живой n8n и файла теперь различается. Последняя ошибка Telegram 404 датирована предыдущим днём, текущую недоступность webhook не доказывает.

Проверка приватного JSON B4 (111 узлов) выявила **две явные заглушки** в включённых HTTP-узлах операторского → клиентского обмена: `Служебный_Запустить отправку публичного события` и `Служебный_Запустить отправку ответа менеджера`, оба содержат `https://SET_KATONA_N8N_HOST/...`. Это не действительные URL. В сервисной конфигурации `kb.vklyuchena=false`, в конфигурации v2 `pozvolit_v2_sql=false`; прямое выполнение новой KB пока заблокировано (если ноды после импорта не редактировались). Стандартный входящий Webhook имеет `headerAuth`, соответствие с Telegram secret_token ещё не проверено.

Безопасный следующий шаг: **деактивировать B4 в UI**, не удаляя и не создавая вторую версию, проверить обе живые исходящие HTTP ноды и наличие соответствующих клиентских endpoints. Пока не включать снова, не загружать Markdown, не выдавать SQL EXECUTE; сначала подготовить отсутствие ложной финальной ошибки и безопасную диагностику.
