# B4 — служебный Workflow: контроль безопасного черновика

Дата: 24.10.2026. Статус: **🔄 В РАБОТЕ; НЕ ВКЛЮЧАТЬ**.

## Исходник

Получен свежий n8n-экспорт служебного Workflow «ЗАКРЫТЫЙ ТЕСТ (1)», 108 узлов, `active=true` в присланном файле. В рабочей n8n включение/отключение по одному экспорту независимо не подтверждалось. Для нового импорта принудительно `active=false`.

## Подготовленный приватный результат B4

Импортируемый **черновик**, 55 нод. В нём сохранены пути:
- регистрация входа в Telegram, подтверждение webhook, запросы захвата;
- синхронизация списка менеджеров, подтверждение callback;
- публикация события захвата во внутренний клиентский webhook;
- ответы менеджеров и отправка в клиентский webhook;
- /start менеджера и подтверждение личного чата.

Credential refs перенесены из свежего экспорта без подмены ролей: служебный Postgres, служебный Telegram, внутренний HTTP Header Auth и Telegram webhook Header Auth. Это проверка полей JSON, **не проверка доступности в живой n8n**.

## Что удалено и заменено

Старая автоматическая KB-очередь `zabrat_zadanie_znaniy`, возвраты `zavershit_zadanie_znaniy` со статусом `povtor`, старая запись бинарного файла `decode(base64)`, старые prepare/save/publish/quality SQL и пятиминутный Schedule Trigger в черновике отсутствуют. Операторская доставка по HTTP с `retryOnFail` сохранена; это не повтор KB-обработки.

Для документов фильтруется `payload_ishodnyy`: в БД идут только Telegram update ID и метаданные документа. Создан маршрут `katona.kb_v2_zaregistrirovat(uuid,bigint,text)` **до скачивания файла**, затем отдельная проверка файла без `kb01a_base64`; сохранены парсер YAML/Markdown, профиль `text-embedding-3-large/1024`, структурное разбиение, подсчёт токенов и подготовка контрольных вопросов. Текст и fragments существуют временно внутри execution, **не записываются** в Supabase при текущем блокирующем конфиге.

Введены `active=false`, `kb.vklyuchena=false`, workflow settings `saveDataSuccessExecution=none`, `saveDataErrorExecution=none`, `saveManualExecutions=false`, `saveExecutionProgress=false`. Сама установка этих полей не подтверждает уничтожение истории предыдущих executions, бинарных файлов или backup; отдельно проверить UI после импорта.

## Не готово — блокирует выпуск

1. Нужен **read-only** контракт из живой Supabase по 10 функциям `kb_v2_*`: точные аргументы, имена полей `RETURNS TABLE`, JSON-ключи. В репозитории нет полных актуальных тел функций.
2. Подключить: prepare → единственный claim → защищённая запись fragments(1024) → запись 3–10 вопросов → проверки → **один** atomic publish. После ошибок — безопасное терминальное завершение `oshibka` или `neizvestno` без второго SQL publish.
3. Довести независимые итоговые сообщения через старый audit outbox и разбор отказов до claim/после claim, остановки workflow и обрыва сети. Не оставлять висящих `prinyata`/ `v_rabote` попыток.
4. Проверить активные Credentials, доступ к функции регистрации для служебной роли (сейчас все права EXECUTE закрыты), фактические настройки выполнения/retention, дубли webhook, тест отмены/просрочки/сетевого unknown и конкуренции.
5. **До завершения 1–4 не включать Workflow, не открывать kb gate, не выдавать EXECUTE**.
