# DASH-03 — технический план реализации

**Статус: документация подготовлена, ни одна задача реализации не начата.** Ничего не устанавливать и не публиковать без отдельного задания/приёмки руководителя проекта.

## Архитектура — принцип

```text
Браузер руководителя
    ↓ аутентификация/авторизация
Отдельное frontend+server приложение дашборда (предлагается Next.js + TS)
    ↓ server-only database adapter / защищённый API
Supabase PostgreSQL, только схема katona
    ↓ минимальные read-only VIEW / SECURITY DEFINER RPC по проверенному контракту
Агрегаты, статусы, безопасные метаданные
```

- React/Next.js, TypeScript, адаптивные графики — **рекомендуемый стек**, подтвердить совместимость с окружением после аудита репозитория/хостинга; не навязывать новые зависимости до D1.
- Схема Supabase **одна на компанию**. Интерфейс и адаптер настраиваются, но не принимают произвольную схему из browser query.
- В репозитории `katona` исходная система пока n8n+Supabase, отдельного frontend нет. Создать проект в `dashboard/` (после этапа D0), не смешивая его с двумя Workflow.
- Предпочтение одной агрегированной серверной выборке либо малому числу запросов; избегать N+1, полной выгрузки истории и дорогого чтения векторов.
- Доступ к БД — через ограниченную серверную роль/защищённые SQL-функции **после проверки** существующей `katona_dashboard_read`. Эта роль в историческом SQL — NOLOGIN; нельзя считать её готовым подключением frontend. Не выдавать прямой доступ клиенту и не использовать `postgres`/`service_role` в браузере.
- Не выставлять внутреннюю n8n, Supabase Studio или PostgreSQL-порт во внешний Интернет ради dashboard.
- Любые SQL изменения (VIEW/FUNCTION/GRANT) — отдельная подготовка, ревью и явное разрешение пользователя. До этого только SELECT/описание.
- ПД/сырой текст диалогов в v1 не нужны; логировать только технические коды ошибок без PII.

## Этапы — одна задача за одну передачу VSCode

### D0 — аудит и подтверждение данных (первый блок)

- [x] Изучить `PLAN.md`, `DB_WORKFLOW_CONTRACT.md`, `DB_AUDIT.md`, `docs/01_BOT_REQUIREMENTS.md` и документы дашборда.
- [x] Найти в репозитории имеющиеся SQL/схемы/контракт `audit_dashboard_summary` и определить, каких полей не хватает для 4 KPI, динамики, воронки и списка.
- [x] Выполнить **только read-only** исследование Supabase **если доступ действительно настроен**, иначе подготовить минимальные SELECT для выполнения пользователем в Supabase SQL Editor. Не спрашивать пароли и не пытаться обходить отсутствие доступа. *(DASH-D0-01: доступа нет, подготовлены SQL-D0-1…7.)*

- [x] Обновить `PLAN.md` только по фактам результата, не объявлять D1 выполненным.

**Выход D0:** руководство получает отчёт VSCode и принимает решение о SQL-контракте. Без подтверждения полей фронтенд не начинать.

### D1 — контракт read-only API

- [ ] После письменного разрешения пользователя внедрить разрешённый backend и покрыть unit/integration тестами на синтетических данных.

**Выход D1:** подтверждённые SELECT/RPC и типизированный backend, без UI.

### D2 — frontend MVP

## Ограничения и качество

- Не изменять `workflows/current/` и не импортировать никаких n8n JSON.
- Не изменять живую схему Supabase до отдельного разрешения. SQL-инвентаризация — строго SELECT/каталог PostgreSQL.
- Не трогать Qbit-схему. Не переносить клиентские данные в GitHub.
- Не делать панель «управления ботом», CRM, редактор знаний, мониторинг API-токенов.
- Данные только реальные либо явно отмеченные тестовые. В интерфейсе production — никаких заглушек с фиктивными KPI.
- В ходе каждой задачи VSCode сообщает изменённые файлы, тесты, коммит, ограничения и следующий шаг. Руководитель проекта утверждает следующий этап по отчёту.

## Отложенные вопросы

1. Реальное содержание `audit_dashboard_summary` и список таблиц/полей, доступных dashboard read.
2. Хранится ли история прохождения этапов и целевых результатов, кто и когда присваивает статус «потерян».
3. Можно ли однозначно отличить переданный менеджеру диалог от ожидающего захвата.
4. Нужна ли отдельная аутентификация пользователей и какие роли будут в v1.
5. Целевой хостинг; пока **локальная разработка**, production домен не выбран.

Блоки D0/D1 независимы от полной продуктовой базы знаний бота; продуктовый RAG после загрузки проверяется отдельно.
