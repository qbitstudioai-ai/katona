# DASH-03 — технический план реализации

**Статус: документация подготовлена, ни одна задача реализации не начата.**

**Обязательное правило:** проектируем сразу полноценную рабочую версию 1.0, без отдельного пилота или урезанного MVP. Проверки и приёмка обязательны до рабочего запуска. Ничего не устанавливать и не публиковать без отдельного задания/приёмки руководителя проекта.

## Архитектура — принцип

```text
Браузер руководителя
    ↓ аутентификация/авторизация
Отдельное frontend+server приложение дашборда (предлагается Next.js + TS)
    ↓ server-only database adapter / защищённый API
Supabase PostgreSQL, только схема katona
    ↓ минимальные read-only VIEW / SECURITY DEFINER RPC по проверенному контракту
Агрегаты, статусы, безопасные метаданные
```

- React/Next.js, TypeScript, адаптивные графики — **рекомендуемый стек**, подтвердить совместимость с окружением после аудита репозитория/хостинга; не навязывать новые зависимости до D1.
- Схема Supabase **одна на компанию**. Интерфейс и адаптер настраиваются, но не принимают произвольную схему из browser query.
- В репозитории `katona` исходная система пока n8n+Supabase, отдельного frontend нет. Создать проект в `dashboard/` (после этапа D0), не смешивая его с двумя Workflow.
- Предпочтение одной агрегированной серверной выборке либо малому числу запросов; избегать N+1, полной выгрузки истории и дорогого чтения векторов.
- Доступ к БД — только через отдельное ограниченное серверное подключение и read-only API (раздел ниже). Не выдавать прямой доступ клиенту и не использовать `postgres`/`service_role` в браузере.
- Не выставлять внутреннюю n8n, Supabase Studio или PostgreSQL-порт во внешний Интернет ради dashboard.
- Любые SQL изменения (VIEW/FUNCTION/GRANT) — отдельная подготовка, ревью и явное разрешение пользователя. До этого только SELECT/описание.
- ПД/сырой текст диалогов в v1 не нужны; логировать только технические коды ошибок без PII.

## Подключение backend к Supabase (решение DASH-D0-03)

**Факт** (`DATA_AUDIT.md` §6): `katona_dashboard_read` — NOLOGIN, доступна только техническая `audit_dashboard_summary()`, прямых прав на таблицы нет. `katona_dashboard_admin` содержит функции изменения данных. Подключения n8n (`katona_n8n_bot_login`, `katona_n8n_service_login`) — рабочие контуры бота и загрузки знаний. **Ни одно существующее подключение дашборд использовать не может**, поэтому backend требует **отдельного ограниченного серверного подключения и безопасного read-only API**.

Рекомендуемая схема — проект для SQL D1. Ничего не создаётся до письменного разрешения пользователя.

1. **Отдельная LOGIN-роль только для сервера дашборда** (рабочее имя `katona_dashboard_api_login`). Она входит только в `katona_dashboard_read`; без прямых прав на таблицы, без доступа к схеме Qbit. Для неё: `default_transaction_read_only = on`, `statement_timeout` и `idle_in_transaction_session_timeout` в секундах, малый `CONNECTION LIMIT`. Пароль хранится только в секретах сервера дашборда, не в GitHub и не в n8n.
2. **Новые read-only функции дашборда в `katona`** (сводка, динамика, этапы, страница диалогов) вместо `audit_dashboard_summary`:
   - `SECURITY DEFINER`, `STABLE`, фиксированный `SET search_path = pg_catalog, pg_temp`, все объекты с префиксом `katona.`;
   - проверка параметров: `from < to`, ограничение длины периода, `limit` не больше 20;
   - на выходе только агрегаты, безопасные поля и `data_as_of`; ПД нет;
   - `REVOKE ALL … FROM PUBLIC`, `GRANT EXECUTE` только `katona_dashboard_read`.
3. **Владелец новых функций — не `postgres`**, в отличие от существующих 12 функций. Это отдельная NOLOGIN-роль с `SELECT` только на нужные таблицы и столбцы: `dialogi`, `celevye_sobytiya`, `sobytiya_etapov`, признак теста `polzovateli`; `zayavki` — только если войдёт в контракт. Ошибка в функции не даст ни записи, ни доступа к остальной схеме.
4. **Сеть.** Сервер дашборда подключается к PostgreSQL по приватной сети или SSH-туннелю, как n8n; при подключении по сети — TLS с проверкой сертификата. Порт PostgreSQL наружу не публикуется. Supabase REST/PostgREST с `anon`/`authenticated`, `service_role` и ключи n8n не используются.
5. **Сервер дашборда** вызывает только фиксированный набор функций с параметрами; SQL-строк из браузера нет. Браузер получает только ответы API после аутентификации руководителя (способ — вопрос 4 ниже). В журналы попадают только технические коды без ПД.
6. **Откат:** удаление новых функций и ролей не затрагивает n8n и существующие права, включая 9 разрешений `kb_v2_*` служебного подключения.

## Ограничения и качество

- Не изменять `workflows/current/` и не импортировать никаких n8n JSON.
- Не изменять живую схему Supabase до отдельного разрешения. SQL-инвентаризация — строго SELECT/каталог PostgreSQL.
- Не трогать Qbit-схему. Не переносить клиентские данные в GitHub.
- Не делать панель «управления ботом», CRM, редактор знаний, мониторинг API-токенов.
- Данные только реальные либо явно отмеченные тестовые. В интерфейсе production — никаких заглушек с фиктивными KPI.
- В ходе каждой задачи VSCode сообщает изменённые файлы, тесты, коммит, ограничения и следующий шаг. Руководитель проекта утверждает следующий этап по отчёту.
