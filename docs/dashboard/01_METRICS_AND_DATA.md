# DASH-01 — метрики и контракт данных Supabase

**Статус: целевая спецификация v1; источники 4 KPI подтверждены read-only аудитом (DASH-D0-02), права доступа и полнота данных — нет.** Все значения вычисляются из Supabase, а не из текстов ответов LLM. Формулы и проверки — в [`DATA_AUDIT.md`](DATA_AUDIT.md).

## Ключевая единица учёта

`dialog_id` — логический диалог. Один пользователь может иметь несколько сообщений и повторные обращения; входящие сообщения **не** должны автоматически увеличивать количество новых диалогов. Точный ключ уникальности, тип статусов, времена и правила переоткрытия необходимо установить по живой схеме.

### Единое временное правило

- Часовой пояс интерфейса v1: `Europe/Moscow`; БД хранит исходные timestamp, предпочтительно `timestamptz`, без ручного прибавления часов.
- Период: полуинтервал `[from, to)` по **времени первого валидного клиентского входа в диалог**. Пограничные тесты обязательны.
- Все 4 основных KPI относятся к **одной когорте** диалогов, впервые поступивших за выбранный период; факт достижения цели и текущий итог оцениваются **на момент запроса**. Историческая цифра за прошлый период может обновиться, если диалог завершился позже; UI должен объяснять это.
- Оперативный счётчик ожидающих менеджера (если реален) — **снимок на текущий момент, не часть когорты**; подписывать отдельно.
- Канал определяется по первому подтверждённому источнику диалога; повторное/дублированное событие не создаёт дополнительное обращение. Возможные миграции каналов — отдельный вопрос для аудита.

## 4 основных KPI

| Код | Пользовательское название | Формула / смысл | Обязательная проверка |
|---|---|---|---|
| `new_dialogues` | Новые обращения | `COUNT(DISTINCT dialog_id)` для первого валидного входа в период | Таблица, тип события, дедупликация, системные/тестовые обращения |
| `target_reached` | Достигли цели | Число диалогов из той же когорты с **подтверждённым** целевым результатом (например, достигнут целевой этап), не просто упоминанием контакта моделью | Где хранится итог и событие достижения; нельзя выводить только из текста LLM |
| `conversion_pct` | Конверсия | `100 * target_reached / new_dialogues`, с оговорённым округлением; при знаменателе 0 — «—», не `0%` | Единая когорта, наличие надёжного признака цели |
| `lost_dialogues` | Потерянные | Число диалогов той же когорты, чей **подтверждённый текущий** бизнес-статус «потерян» | Список реальных значений статуса, блокировка/отказ не обязательно равны потере |

**Не подменять цель:** в проекте v1 «конверсия» определялась как доля диалогов, дошедших до целевого этапа. Конкретные названия столбцов и допустимых этапов надо подтвердить; в настройках бота целевой сценарий — запросить расчёт/замер или передать специалисту, а `имя` и `телефон` могут быть отдельными полями лида. Различать «достиг целевого этапа» и «контакт получен». В случае отсутствия истории этапов нельзя считать историческую конверсию по одному текущему этапу без обсуждения.

## Остальные элементы, не отдельные KPI-карточки

| Элемент | Определение / поле | Статус |
|---|---|---|
| Динамика обращений | Число **новых диалогов** по локальным дням внутри выбранной когорты | Из первичного события, проверить |
| Динамика достижения цели | При необходимости рядом со столбцами новых диалогов: число достигших цели **из когорт соответствующих дней**, как на момент просмотра | Вторая серия — только если факты доступны; иначе одна |
| Воронка / этапы | Последовательные этапы с подсчётом **достигавших** каждого этапа. Не считать «достигавших» по текущему этапу, если возможны возвраты | Не подтверждено: нужна история переходов; fallback — распределение текущих статусов/этапов с другим заголовком |
| Ожидают менеджера | Число диалогов, требующих человеческого ответа сейчас, только если источник чётко отделяет «передано», «запрошено» и «взято» | Оперативный индикатор без периодной фильтрации, при отсутствии признака скрыть |
| Последние диалоги | Время первого/последнего события, канал, стадия, статус, признак достижения цели, ответственный при наличии | Запрещены телефон, Telegram ID, сырой текст и имя в общей таблице v1 |

## Цель, заявка, дубли, потери и пилотные данные

### `celevye_sobytiya` и `zayavki`

- Целевое событие пишется в `celevye_sobytiya` функцией `zafiksirovat_rezultat_ishodyashchego` только после подтверждённой отправки сообщения клиенту и проверки актуальности состояния диалога. До этого `sozdat_ishodyashchee_deystvie` требует текстовый признак согласия клиента, а `audit_goal_ready` — подтверждённые имя и телефон. Предложение LLM перейти на целевой этап само по себе цель не фиксирует.
- При `kod_celi='ostavit_zayavku'` и выполнении условий из того же события создаётся строка `zayavki`. Заявка — **производная** от целевого события: не каждое событие обязано дать заявку, но заявка без события — аномалия для проверки.
- KPI «Достигли цели» считается по `celevye_sobytiya` с кодом цели компании (`ostavit_zayavku`), а не по `zayavki`, этапу или полям лида. Отдельный KPI «Заявки» в v1 не вводим; расхождение «события без заявки» — контрольная проверка, а не показатель.

### Дубли

- **Обращение.** Новая строка `dialogi` создаётся, только если у идентификатора канала нет незавершённого диалога; повторные входные события отсекаются на входе. Считаем `COUNT(DISTINCT` ключа `dialogi)`, а не сообщения или входные события. Новое сообщение после закрытия диалога — новое обращение.
- **Цель.** Диалог учитывается один раз, сколько бы целевых событий у него ни было (`EXISTS`/`DISTINCT`). Допускает ли схема несколько событий одного кода на диалог — проверить.
- **Время.** Когорта — только по `dialogi.vremya_nachala`; время целевого события, заданий обработки и исходящих сообщений в фильтр периода не входит.

### Потери

- Потерян = текущее `dialogi.status='zavershen'` **и** `rezultat='net_otveta'`. Это ставит `zafiksirovat_poteryu_bez_otveta` после подтверждённого второго напоминания без ответа клиента.
- Запрет общения, отказ и другие итоговые значения `rezultat` потерей не считаются без отдельного решения.
- Диалог с подтверждённой целью не может быть потерянным; пересечение проверяется агрегатом и должно быть 0.

### Пилотные данные

- Признак `testovyy` у текущих тестировщиков равен `false`, поэтому надёжного исключения тестовых данных **нет**. Отключать фильтрацию «по умолчанию» или угадывать тестовых пользователей по ID нельзя.
- Варианты для решения руководителя (реализация — только после решения и разрешения пользователя):
  1. Граница запуска: в отчёт попадают только диалоги с `vremya_nachala` ≥ даты допуска реальных покупателей (параметр конфигурации дашборда, без изменения БД).
  2. Проставить `testovyy=true` пилотным пользователям — это изменение данных Supabase, требует отдельного разрешения.
- До решения любые цифры дашборда на живой БД — **пилотные** и помечаются в интерфейсе явно.

### Воронка

Полноценная воронка («сколько диалогов достигало каждого этапа») показывается только после проверки **всех маршрутов** смены этапа: создание диалога, подтверждённые исходящие, запрос менеджера, захват и возврат оператором, ручные сообщения менеджера, предупреждения/блокировка, закрытие потерей. Пока хотя бы один маршрут меняет этап без записи в `sobytiya_etapov` — показываем «Распределение по текущим этапам» и не считаем конверсию между ступенями.

## Обязательные свойства вычислений

- Один согласованный backend-adapter; **никаких** SQL-строк/ролей с широкими привилегиями в браузере.
- Диапазон ограничен, сортировка и limit применяются в БД; не скачивать все диалоги в браузер ради подсчётов.
- Пустой период — «нет обращений», конверсия «—»; ошибка источника — видимая ошибка, а не фиктивные нули.
- Считать `distinct dialog_id` и защититься от дублированных входов, ошибок webhook и повторных задач.
- Не смешивать временные метки обработки задания с временем поступления обращения.
- Синтетические данные и реальные SQL-результаты должны давать одинаковые показатели. Отдельно проверить границы дат, нулевую выборку, отказы, передачи человеку, позднее достижение цели.
- В API возвращать только агрегаты/безопасные метаданные и признак `data_as_of` (время формирования снимка), а не персональные данные.

## Минимальные контракты API (проект, без реализации)

- `GET /api/dashboard/summary?from=...&to=...&channel=...` → `new_dialogues`, `target_reached`, `conversion_pct`, `lost_dialogues`, `data_as_of` плюс сведения о доступности метрики.
- `GET /api/dashboard/trend?...` → локальная дата, новые обращения, (опционально) достигли цели.
- `GET /api/dashboard/stages?...` → либо подтверждённая cumulative funnel, либо распределение текущих этапов; тип визуализации в ответе обязателен.
- `GET /api/dashboard/dialogs?...&cursor=...` → только безопасные поля, ограниченная страница.
- `GET /api/dashboard/attention` → оперативная очередь менеджера, только если подтверждены источник и права.

Это **предлагаемые интерфейсы**, не существующие endpoints. После аудита допускается один `/api/dashboard`-endpoint с типизированными частями вместо пяти, если это проще и быстрее без лишних запросов.

## Аудит источника перед реализацией

VSCode обязан доказать каждую связь `metric → источник → SQL-фильтр → формула → тест-кейс`. Ни одного KPI «просто потому что он полезен» без подтверждённых полей. Итог — `DATA_AUDIT.md` в этой папке с таблицей полей, SQL-функций и прав, без персональных значений и паролей. Аудит не делает `CREATE`/`ALTER`/`GRANT`/`UPDATE` и не трогает Supabase данные.
