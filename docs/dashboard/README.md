# Катона — дашборд руководителя

**Статус: проектная документация; реализация не начата.** Решение от 28.10.2026.

## Назначение

Отдельный web-дашборд руководителя, показывающий короткую сводку работы бота и менеджеров **по фактическим данным из схемы Supabase `katona`**. Не превращать дашборд в CRM, редактор знаний, систему ручного управления Workflow или аналитический комбайн.

Руководитель за 15–30 секунд должен понять: сколько новых обращений, сколько доведено до цели, какова конверсия, сколько потеряно и какие диалоги требуют внимания.

## Границы v1

- Один клиент / одна схема `katona`. Архитектура допускает отдельный экземпляр приложения на клиента и конфигурируемую схему в будущем, **без смешения данных компаний**.
- Источник истины — Supabase PostgreSQL. Без демонстрационных чисел в рабочем интерфейсе, ручных подсчётов по n8n Executions и выдуманных показателей.
- Telegram — текущий подтверждённый канал. Фильтр по каналам показываем, когда существуют минимум два реально подключённых канала.
- 4 KPI, один график динамики, одна компактная визуализация воронки/результатов, таблица последних обращений и ненавязчивый индикатор запросов менеджеру. Подробности — в `02_UX_AND_FILTERS.md`.
- Нет финансового учёта, расходов LLM, «себестоимости диалога», сложных рейтингов менеджеров, CRM-сделок, прогнозов, графиков ради графиков.
- Дашборд **только чтение**. Не редактирует статусы, сообщения, документы и правила бота.

## Правило точности данных

В репозитории подтверждены наличие схемы `katona`, ограниченной роли `katona_dashboard_read` (NOLOGIN) и историческое упоминание SQL-функции `audit_dashboard_summary`. **Этого недостаточно**, чтобы утверждать существование таблиц/полей, необходимых для каждого KPI, или фактическую доступность API дашборда.

Поэтому:
1. Сначала VSCode делает **только чтение**: инвентаризацию структуры схемы, доступных функций, прав и полей, используемых для метрик.
2. По результату руководитель проекта утверждает формулы и контракты; неподтверждённые метрики маркируются как ожидающие источника.
3. Только затем — backend и UI. Никогда не заменять отсутствующие данные нулями: показывать «нет данных»/«метрика пока недоступна».

## Разделение ответственности

**ChatGPT — руководитель проекта:** читает репозиторий и отчёт VSCode, определяет один очередной шаг, принимает решения, проверяет соответствие требованиям. **Пользователь — оркестратор:** передаёт промпт VSCode и возвращает отчёт. **VSCode — исполнитель:** read-only аудит, код, тесты и документация строго в указанном объёме. Новые изменения в боевых Supabase, n8n и клиентском Workflow не делать без отдельного разрешения пользователя.

## Зависимости

Полная загрузка базы знаний **не нужна** для проектирования дашборда. Но реальный проверенный источником набор клиентских диалогов и их статусов нужен для интеграционного теста. Отложенные проверки знаний бота продолжатся **после** полной загрузки базы. В клиентский Workflow до этого не вносим изменений.

Указанные в старых файлах `PLAN.md` статусы 21–26 октября являются **историей**, а не инструкцией заново развёртывать уже работающий Telegram-мост.
