# KAT-KB-RETRY-01B3 — проект безопасной БД для одной попытки

**Статус:** 🔄 в работе с 23.10.2026. **B3.1 ✅, B3.2 ✅, B3.3 ✅, B3.4 ✅ по отчёту пользователя; B3.5 🔄.** Пользователь выполнил ранее предоставленный DDL B3.4 в Supabase, затем получил четыре `OK` по read-only проверке. Эти проверки подтверждают существование таблицы, nullable bytes и двух индексов, **но не проверяют все ограничения или права доступа**. Функции v2/JSON ещё не применялись; активные данные не удалялись.

## Задача и правила

Создать путь загрузки знаний Катоны: одна попытка обработки каждого нового Telegram-документа, без автоматических повторов, без долговременного сохранения исходного Markdown/base64 в Supabase и n8n. Финальное уведомление в Telegram независимо от успеха публикации. Клиентский RAG, действующие опубликованные версии, Qbit и остальные части служебного бота не менять.

Три read-only отчёта B2 и фактический аудит n8n описаны в [отчёте B2](10_KB_RETRY_01B2_READ_ONLY_AUDIT.md). **Три триггера и обязательные поля/ограничения из B3.1 проверены**; перед исполняемым проектом остались уточнения действующей очереди уведомлений, уникальных индексов и поля-IDENTITY.

## Рабочий вариант (требует подтверждения зависимостей)

1. Сохранить существующие `katona.dokumenty_znaniy`, `versii_dokumentov_znaniy`, `fragmenty_znaniy`, векторы `vector(1024)`, текущий active pointer и профиль индекса.
2. Сохранить запись загрузки в `katona.zagruzki_znaniy` как **метаданные без bytes** (для совместимости FK существующих версий, очередей и аудита). Для новой регистрации может потребоваться `ALTER COLUMN ishodnyy_fayl DROP NOT NULL` — **не выполнять** до проверки триггеров и зависимостей; новая функция не должна принимать, читать или сохранять исходные bytes.
3. Добавить отдельную таблицу попыток v2 с уникальным ключом Telegram-события и полями: id, zagruzka_id, dokument_id, versiya_id, status, номер владения, срок операции, минимальные коды ошибок, timestamps. **Без** Markdown, binary, base64, фрагментов, vectors и полных ошибок. Предпочтительна ссылка на `sobytiya_integraciy`/идентификатор события, чтобы повтор Telegram update не создавал новую попытку.
4. **Повторно использовать существующую таблицу `katona.audit_uvedomleniya`**: B3.2 подтвердил `UNIQUE (klyuch)`, статус, чат, thread, worker, lease, число попыток. Триггер `audit_kb_notice` создаёт одну запись по ключу при переходе загрузки в `zavershena`/`oshibka`. **UNIQUE предотвращает повторную вставку, но не гарантирует однократную доставку Telegram** (при неизвестном ответе Telegram). Новый путь не должен дополнительно отправлять успех/ошибку второй очередью. `neizvestno` требует отдельной единственной записи (с новым уникальным ключом), не запускающей обработку.
5. Новые `SECURITY DEFINER` функции v2 для регистрации метаданных, единственного взятия задачи, подготовки версии, сохранения фрагментов/вопросов/проверок, атомарной публикации, финального статуса, read-only сверки и безопасной очистки. Каждая запись/публикация проверяет id попытки, текущий статус, номер владения, срок и принадлежность версии; состояние `otmenena`/закрытая попытка блокирует позднего worker. Старые `zabrat_zadanie_znaniy` и `povtor` новая ветка **не вызывает**.
6. При ошибке помечать только связанную неактивную версию как failed и удалять её временные фрагменты/вопросы/векторы по проверенным FK. Ни при каких условиях не удалять действующую опубликованную версию или другой документ.
7. В n8n B4 потребуется отдельная безопасная KB-ветка/Workflow, который сам скачивает файл после регистрации метаданных, не сохраняет executions с содержимым, не переносит base64 в сохраняемый JSON и отключает `retryOnFail`. Только настройки текущего Workflow менять недостаточно; если родительский Workflow сохраняет binary, это тоже нужно исключить.

## Контракт состояния попытки

`prinyata → v_rabote → opublikovana | oshibka | neizvestno`; `otmenena` — отдельный защищённый финал. Финальные состояния не возвращаются в `v_rabote`. Новая отправка файла в Telegram — новое событие, а повтор **того же события** возвращает предыдущий результат. Истечение срока операции не приводит к новому запуску; для неизвестной публикации только проверка состояния без второго publish.

## Проверки, необходимые перед точным SQL

- Реальные определения пользовательских триггеров и их функций для `zagruzki_znaniy`, `dokumenty_znaniy`, `profili_indeksa`, `versii_dokumentov_znaniy`: что записывают в audit и что запрещают.
- Все CHECK/FK/NOT NULL/DEFAULT, затрагивающие `zagruzki_znaniy` и `versii_dokumentov_znaniy`, чтобы новая версия могла ссылаться на регистрацию **без исходного файла**.
- Проверить имена/права существующих функций и принцип минимальных EXECUTE для `katona_n8n_service_login`; никогда не давать этой роли прямых прав на таблицы.
- До запуска проверить real n8n execution/history retention, настройки провайдера по snapshots/backup. Полное физическое уничтожение старых копий без этого не подтверждено.

## Результат B3.1 — проверенный отчёт Supabase

Источник: 100 строк read-only SQL Editor от пользователя (41 CONSTRAINT, 56 REQUIRED_COLUMN, 3 TRIGGER); значения реальных записей и документы не выгружались.

- **Активная версия защищена:** `ct_dokumenty_aktivnaya_versiya` и `katona.kb_proverit_aktivnuyu_versiyu()` запрещают active pointer на неопубликованную версию или версию другого документа. **Но** не проверяют статус/владельца/аренду исходного задания — публикации v2 нужна отдельная защита.
- **Профиль индекса:** `tr_profili_immutable` запрещает обновлять/удалять профиль, если он используется версией. Переиспользовать старый профиль только с точно совпадающими `1024` измерениями и конфигурацией.
- **Существующее автоматическое KB-уведомление:** `audit_kb_notice` на `katona.zagruzki_znaniy` вызывает `katona.audit_sobytie()`. При переходе в `zavershena`/`oshibka` функция **вставляет** строку в `audit_uvedomleniya` с ключом `kb:<upload-id>:<status>`, `chat_id` и текстом. **Прямой Telegram-отправки сама функция не делает**; наличие и надёжность отправителя ещё не проверены. Возможен дубль уведомления при второй v2-очереди.
- **Старые внешние ключи:** `versii_dokumentov_znaniy.zagruzka_id uuid NOT NULL` требует ссылку на `zagruzki_znaniy`; у `zagruzki_znaniy.ishodnyy_fayl bytea NOT NULL` исходный файл обязателен. Для совместимости с существующими версиями и RAG наиболее безопасный кандидат — допускать `NULL` только в legacy-поле bytes, создавать новую запись метаданных без bytes, **но** эту миграцию пока не применять.
- **Событие:** `sobytiya_integraciy.payload_ishodnyy jsonb NOT NULL` — будущий путь регистрации должен передавать **только безопасные поля Telegram**, не Markdown и не base64. Остальные обязательные поля и CHECK подтверждены.
- **Поле `zagruzki_znaniy.poryadok_priema bigint NOT NULL`** показано как без default; из прежнего аудита известно об одном IDENTITY в схеме, но **не доказано**, что он именно здесь. Перед подготовкой `INSERT` нужна отдельная проверка `attidentity`.
- Для `audit_uvedomleniya` B3.1 **не запрашивал** ограничения и индексы. Утверждать, что текущий outbox надёжный или годится для v2, пока нельзя.

**Инженерное решение по B3.2:** подтверждена возможность использовать существующий outbox по уникальному ключу, без отдельной таблицы. Новый v2 путь не принимает bytes в SQL, ведёт собственное состояние попытки, блокирует повторную работу и позднюю публикацию; завершает старую запись загрузки один раз, чтобы сработал единственный старый триггер. Перед точным SQL осталось подтвердить семантику `audit_claim_notice`, `audit_finish_notice`, `audit_operational_notices` (без раскрытия секретов).

## Результат B3.2 — существующая очередь и индексы

Источник: read-only SQL Editor, ответ пользователя от 24.10.2026.

- `katona.audit_uvedomleniya` есть; обязательны `id uuid`, `klyuch text`, `chat_id text`, `tekst text`, `status text`, `popytki integer`, `vremya_sozdaniya timestamptz`. Необязательны `thread_id`, `worker`, `arenda_do`, `opisanie_oshibki`.
- `audit_uvedomleniya_klyuch_key UNIQUE (klyuch)` и CHECK статусов `zaplanirovano`, `v_rabote`, `podtverzhdeno`, `neizvestno`, `oshibka`. Это **не** гарантия ровно одного сообщения Telegram после сетевого обрыва.
- Получающие/закрывающие очередь функции: `katona.audit_claim_notice(jsonb)`, `katona.audit_finish_notice(jsonb)`; также `audit_operational_notices()`. Наличие функций проверено, **содержимое ещё неизвестно**.
- Интеграционное событие: уникальные `(istochnik,akkaunt_istochnika_id,vneshnee_sobytie_id)` и `klyuch_idempotentnosti`. Загрузка: уникальный `sobytie_integracii_id`. Задание: уникальный `(zagruzka_id,tip_zadaniya)`, а также частичный уникальный `(dokument_id)` при `v_rabote`. Версия: уникальный `(dokument_id,nomer_versii)`.
- `katona.zagruzki_znaniy.poryadok_priema` — `GENERATED ALWAYS AS IDENTITY`. В проекте v2 **не заполнять вручную**.
- Решение: **использовать существующий outbox** с единственным уникальным ключом события/итога; SQL v2 проектировать только после проверки claim/finish, не создавать конкурирующую очередь.

## Результат B3.3 — функции выдачи и доставки (отчёт пользователя)

Источник: 63 строки SQL Editor (59 столбцов, 4 определения функций).

- `katona.audit_claim_notice(jsonb)`: при просроченной `v_rabote` переводит запись уведомления в `neizvestno`, **не возвращая** в `zaplanirovano`. Новую запись выбирает через `FOR UPDATE SKIP LOCKED`, ставит lease 2 минуты и выдаёт chat/thread/text/worker. Это не повтор KB-обработки.
- `katona.audit_finish_notice(jsonb)`: разрешает закрыть запись только текущему worker и только из `v_rabote`; `ok=true` → `podtverzhdeno`, остальные исходы → `neizvestno`. **Текст `error` сохраняется в `opisanie_oshibki` без очистки**: новый Workflow передаёт лишь краткий разрешённый код, не сырые исключения.
- `katona.audit_operational_notices()`: добавляет уведомления по неизвестным результатам зеркалирования/тем и ошибкам скачивания вложений; автоматический повтор KB в функции отсутствует. KB уведомления создаёт `audit_sobytie()`.
- **Критично:** `katona.zaregistrirovat_sluzhebnoe_sobytie(jsonb)` сохраняет `payload_ishodnyy` практически без ограничения списка полей и при дубликате возвращает его; поэтому новая KB-ветка должна подавать **только белый список безопасных метаданных**. Не включать туда Markdown, base64, document.text, полные output/error.
- Проверены полные поля `dokumenty_znaniy`, `versii_dokumentov_znaniy`, `zadaniya_znaniy`, `zagruzki_znaniy`: `zagruzki_znaniy.ishodnyy_fayl bytea NOT NULL`; `versii_dokumentov_znaniy.zagruzka_id uuid NOT NULL`; `zagruzki_znaniy.poryadok_priema GENERATED ALWAYS AS IDENTITY`; `zadaniya_znaniy.nomer_vladeniya bigint default 0`. В новом v2 не использовать legacy job table, чтобы старый `zabrat_zadanie_znaniy` не мог подхватить и повторить новую задачу.

### B3.4 — проект DDL только в чате (содержание, не SQL-файл)

1. Проверить живой тип и `NOT NULL` legacy-поля `ishodnyy_fayl`. Предполагаемое изменение `ALTER COLUMN ... DROP NOT NULL` допускает метаданные без bytes, **не удаляет существующие данные** и не меняет legacy функции.
2. Добавить одну таблицу `katona.kb_popytki_v2`: ID попытки, `zagruzka_id` и `sobytie_integracii_id` с `UNIQUE`, опциональные `dokument_id`/`versiya_id`, `status`, `nomer_vladeniya` (0 либо 1), токен владельца и срок, безопасный короткий код ошибки, даты. Нет `bytea`, Markdown, base64, полных JSON или текстов исключений.
3. Частичный уникальный индекс для одного `v_rabote` на логический документ; ограничения финальных статусов. **Одним DDL добиться zero-retry нельзя**: новые SECURITY DEFINER функции должны атомарно выдавать задачу ровно один раз (нет возвращения из финальных статусов), проверять токен во всех записях и защищать публикацию. Их проектировать и проверять отдельным следующим блоком.
4. Никаких прав на новую таблицу n8n напрямую. Выдавать `EXECUTE` лишь на новые функции после проверки; не трогать опубликованную версию/векторные данные.

**Откат DDL:** при сбое новой ветки отключить вход v2 и сохранить новую таблицу для диагностики; `DROP NOT NULL` не откатывать автоматически, если появились записи с `NULL`. Старые активные знания останутся доступны. Ни один SQL из B3 не исполняется до отдельного разрешения пользователя.
