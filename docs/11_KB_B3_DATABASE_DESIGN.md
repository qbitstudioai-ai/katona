# KAT-KB-RETRY-01B3 — проект безопасной БД для одной попытки

**Статус:** 🔄 в работе с 23.10.2026. **Только проект; ни SQL, ни JSON на сервере не применялись.**

## Задача и правила

Создать путь загрузки знаний Катоны: одна попытка обработки каждого нового Telegram-документа, без автоматических повторов, без долговременного сохранения исходного Markdown/base64 в Supabase и n8n. Финальное уведомление в Telegram независимо от успеха публикации. Клиентский RAG, действующие опубликованные версии, Qbit и остальные части служебного бота не менять.

Три read-only отчёта B2 и фактический аудит n8n описаны в [отчёте B2](10_KB_RETRY_01B2_READ_ONLY_AUDIT.md). **Нельзя считать проект готовым для выполнения, пока не просмотрены функции триггеров и ограничения.**

## Рабочий вариант (требует подтверждения зависимостей)

1. Сохранить существующие `katona.dokumenty_znaniy`, `versii_dokumentov_znaniy`, `fragmenty_znaniy`, векторы `vector(1024)`, текущий active pointer и профиль индекса.
2. Сохранить запись загрузки в `katona.zagruzki_znaniy` как **метаданные без bytes** (для совместимости FK существующих версий, очередей и аудита). Для новой регистрации может потребоваться `ALTER COLUMN ishodnyy_fayl DROP NOT NULL` — **не выполнять** до проверки триггеров и зависимостей; новая функция не должна принимать, читать или сохранять исходные bytes.
3. Добавить отдельную таблицу попыток v2 с уникальным ключом Telegram-события и полями: id, zagruzka_id, dokument_id, versiya_id, status, номер владения, срок операции, минимальные коды ошибок, timestamps. **Без** Markdown, binary, base64, фрагментов, vectors и полных ошибок. Предпочтительна ссылка на `sobytiya_integraciy`/идентификатор события, чтобы повтор Telegram update не создавал новую попытку.
4. Сделать отдельную таблицу исходящих уведомлений v2 с безопасным типом сообщения/адресатом и состоянием доставки. Допустим **повтор доставки сообщения**, но не обработки файла.
5. Новые `SECURITY DEFINER` функции v2 для регистрации метаданных, единственного взятия задачи, подготовки версии, сохранения фрагментов/вопросов/проверок, атомарной публикации, финального статуса, read-only сверки и безопасной очистки. Каждая запись/публикация проверяет id попытки, текущий статус, номер владения, срок и принадлежность версии; состояние `otmenena`/закрытая попытка блокирует позднего worker. Старые `zabrat_zadanie_znaniy` и `povtor` новая ветка **не вызывает**.
6. При ошибке помечать только связанную неактивную версию как failed и удалять её временные фрагменты/вопросы/векторы по проверенным FK. Ни при каких условиях не удалять действующую опубликованную версию или другой документ.
7. В n8n B4 потребуется отдельная безопасная KB-ветка/Workflow, который сам скачивает файл после регистрации метаданных, не сохраняет executions с содержимым, не переносит base64 в сохраняемый JSON и отключает `retryOnFail`. Только настройки текущего Workflow менять недостаточно; если родительский Workflow сохраняет binary, это тоже нужно исключить.

## Контракт состояния попытки

`prinyata → v_rabote → opublikovana | oshibka | neizvestno`; `otmenena` — отдельный защищённый финал. Финальные состояния не возвращаются в `v_rabote`. Новая отправка файла в Telegram — новое событие, а повтор **того же события** возвращает предыдущий результат. Истечение срока операции не приводит к новому запуску; для неизвестной публикации только проверка состояния без второго publish.

## Проверки, необходимые перед точным SQL

- Реальные определения пользовательских триггеров и их функций для `zagruzki_znaniy`, `dokumenty_znaniy`, `profili_indeksa`, `versii_dokumentov_znaniy`: что записывают в audit и что запрещают.
- Все CHECK/FK/NOT NULL/DEFAULT, затрагивающие `zagruzki_znaniy` и `versii_dokumentov_znaniy`, чтобы новая версия могла ссылаться на регистрацию **без исходного файла**.
- Проверить имена/права существующих функций и принцип минимальных EXECUTE для `katona_n8n_service_login`; никогда не давать этой роли прямых прав на таблицы.
- До запуска проверить real n8n execution/history retention, настройки провайдера по snapshots/backup. Полное физическое уничтожение старых копий без этого не подтверждено.

**Откат:** новый KB-путь отключается независимо от старого, действующий клиентский RAG остаётся. Удаление/замена старых функций, таблиц, контента и активных версий в B3 не допускается. Старый worker с автоповторами не возвращать как «откат». Новые таблицы/функции не удалять до проверки, что нет ссылок и незавершённых операций.

**Важно:** два старых TEST-файла (8 944 bytes) в Supabase **не очищены**; их адресная очистка — отдельная согласованная операция, не часть автоматического запуска B3.
