# KAT-KB-RETRY-01 — безопасные повторы, ошибки и отмена загрузки знаний

**Статус:** проект решения; реализация, изменения живой базы и n8n НЕ выполнялись.
**Дата:** 23.10.2026.
**Источник:** служебный TEST Workflow Катоны (`workflows/current/`), `DB_WORKFLOW_CONTRACT.md` Катоны; как справочный исходник — `sql/DB-04_05_knowledge_recreate_test.sql` и `docs/specs/KNOWLEDGE_INGESTION.md` исходного шаблона. Фактический SQL Катоны после переноса нужно прочитать отдельно: нельзя утверждать, что он полностью совпадает с исходником.

## Наблюдаемая проблема

- Telegram Webhook доставляет сообщения, Markdown зарегистрирован в Supabase (это НЕ публикация).
- Дальнейшие проверки worker завершились в ноде `KB-01B2 Итог без возврата`:
  `prepare_rezultat=povtor`, `kod_oshibki=dokument_zanyat`,
  `opisanie=Другой worker уже обрабатывает этот logical document`.
- Ни один просмотренный запуск не дошёл до `KB-03C1 Итог публикации`.
- Павел отключил Schedule Trigger «Проверять очередь знаний каждые 5 минут» и опубликовал изменение; Running executions нет. Периодический recovery остановлен, но входящий документ всё ещё запускает worker сразу по ветке `KB-01A Запустить обработку знаний?`.
- `dokument_zanyat` — конфликт между задачами/арендами, а НЕ доказательство неправильного формата Markdown. Нужно отдельно выяснить, существует ли другая задача `v_rabote`, не истёк ли `arenda_do`, какой `zadanie_id`/lease owner, какова история попыток.
- В служебном JSON ряд проверок формата или профиля отправляет в `zavershit_zadanie_znaniy` статус `povtor` независимо от возможности исправления ошибки повтором. Оповещение об окончательном результате загрузки отсутствует на многих worker-ветках.
- Исходный DB-04/05 шаблона содержит `popytki` и поля lease/fencing, но не содержит очевидного предела числа попыток в `zabrat_zadanie_znaniy`. Это нужно перепроверить в живой Катоне.

## Почему очередь оставляем

Надёжный Telegram ingress должен быстро сохранить исходные bytes и задание в защищённой базе. Разбор, разбиение, embeddings, контрольные вопросы и атомарная публикация занимают больше времени. Повтор нужен для временных сбоев (OpenAI 429/5xx, сетевой timeout, краткая недоступность Supabase, падение worker). Конкурентный claim, lease и fencing защищают от двух одновременных публикаций одного logical document. Ошибка Telegram-уведомления после успешной публикации НЕ должна повторно публиковать документ.

## Предлагаемое конечное поведение

| Ситуация | Состояние и действие | Telegram-отчёт |
| --- | --- | --- |
| Неверный UTF-8, YAML, Markdown, неправильные поля, неделимый фрагмент | Терминальное `oshibka` или документированное `ozhidaet_proverki`; повтор старых bytes запрещён. Новый исправленный файл — новое событие/загрузка | Файл, стадия, понятная причина и что исправить |
| Не хватает контрольных вопросов или проверки качества не пройдены | Не публиковать; перевести в `ozhidaet_proverki` или конечную ошибку до исправления/ручного решения; прежняя активная версия остаётся | Сколько вопросов нужно либо что не прошло и как исправить |
| Временная техническая ошибка API/сети/базы | Ограниченные повторы: предложение для TEST — всего три попытки (сразу, затем через 5 и 15 минут). После исчерпания — `oshibka` и ручной разбор, без бесконечного цикла | Промежуточный статус по запросу; одно итоговое уведомление при исчерпании |
| `dokument_zanyat` | Это не ошибка файла. Найти другое `v_rabote` задание; не выпускать дублирующую публикацию. Ограничить ожидание по времени с учётом lease (TEST: предлагаем диагностическую остановку после 30 минут), уведомить администратора. Не снимать lock вслепую | «Документ ждёт завершения предыдущей обработки»; затем конкретная диагностика, если ожидание затянулось |
| Успешная публикация | Атомарно сменить активную версию только после всех checks; завершить upload/job, отменить ожидающие попытки | Одно уведомление «Опубликован», идентификатор, версия, число фрагментов |
| Дубликат Telegram update или неизменённая активная версия | Не создавать повторное задание и не пересчитывать embeddings | Объяснить, что уже обработано, без повторной «публикации» |
| Администратор отменил ожидающую загрузку | Атомарно `otmeneno` для конкретного job/upload. Если `v_rabote`, сначала fenced cancel/отмена будущего commit; завершения старого worker не должны публиковать. **Не удалять** данные/историю. Опубликованную версию не откатывать как «отмену загрузки» | «Загрузка отменена» после подтверждения БД |

## Доставка сообщений и интерфейс

1. Сразу после регистрации: Telegram сообщает только «Файл принят в очередь, это не публикация» и даёт короткий идентификатор загрузки.
2. По завершении — ровно один логический итог на каждую загрузку: `opublikovana`, `oshibka`, `ozhidaet_proverki` или `otmenena`. Использовать сохранённое намерение уведомления с idempotency key; считать доставленным только после подтверждения Telegram API. Не обещать абсолютное отсутствие дублей внешнего API при неизвестном результате.
3. Дать уполномоченному сотруднику запросить статус и отмену конкретной загрузки (предлагаемые команды `/kb_status <id>`, `/kb_cancel <id>`; **ещё не реализованы**). Авторизация по server-side allowlist, никакого выбора схемы из Telegram. Для отмены running-job нужны fenced/check/version guards в БД; одной Telegram-кнопки недостаточно.
4. В Telegram указывать имя файла, без внутренних секретов, сырых документов и stack trace. Для ошибки по качеству давать конкретное исправление; для технической — безопасное описание и номер обращения.
5. Ошибка доставки Telegram-отчёта не запускает повторную загрузку знаний и не отменяет успешно опубликованную версию. Уведомления имеют независимую очередь/учёт результата.

## Где размещать логику

- **Supabase `katona`** — источник истины: job status, `popytki`, `sleduyushchiy_zapusk`, lease/owner/fencing, терминальный исход, разрешение/запрет публикации, отдельный идемпотентный outgoing intent для Telegram. Границы количества попыток и отмены должны соблюдаться транзакционно, а не только при проверке ноды n8n.
- **n8n** — проверяет известные типы ошибок, вызывает строго ограниченные DB-функции, выполняет внешние API и отправляет уведомления. Ошибку в `Code`-ноде не считать публикацией. Задача `dokument_zanyat` не может обрабатываться как «невалидный Markdown».
- **Конкуренция:** разобраться, как исходный SQL ищет `v_rabote` задания без сопоставления срока `arenda_do` и отчего назначенный worker возвращается в `dokument_zanyat`. Нельзя самостоятельно менять владельца, lease и статус работающей публикации.

## Критерии готовности будущей реализации

- Некорректный файл останавливается после одной содержательной проверки; Telegram сообщает точную причину; старые bytes не крутятся по расписанию.
- Временный сбой автоматически повторяется не больше установленного лимита, затем переводится в терминальное состояние и сообщает результат.
- Lock/busy не вызывает вечной гонки; expired lease обрабатывается корректно, конкурентная публикация запрещена.
- Уведомления связаны с конкретной загрузкой, не дублируются при обычных повторных DB-вызовах; публикация не откатывается из-за Telegram-ошибки.
- Авторизованная отмена останавливает только выбранное ожидающее/running задание; late/stale worker не публикует отменённую версию; уже опубликованные знания и другие компании не затронуты.
- Подтвердить тестами: корректный .md, YAML/контрольные ошибки, OpenAI 429/5xx, аренда/сбой worker, конкурентные job, ручная отмена, Telegram notification failure и повтор Telegram update.
- Перед включением расписания повторить проверку PostgreSQL и Telegram Credentials, исключить Qbit-ID/секреты из публичного JSON.

**Безопасный текущий режим:** Schedule Trigger отключён Павлом в живом служебном Workflow; Running executions не было. Не отправлять новых документов до диагностики; служебный Telegram и остальные операции без необходимости не отключать.
