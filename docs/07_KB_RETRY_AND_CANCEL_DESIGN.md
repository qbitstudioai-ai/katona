# KAT-KB-RETRY-01 — однократная обработка документов и уведомления в Telegram

**Статус:** бизнес-решение принято 23.10.2026; проектирование, без реализации.
**Важно:** работающие SQL-функции, текущий n8n и Supabase этим документом НЕ изменены.
**Основа:** актуальный служебный TEST Workflow Катоны, DB_WORKFLOW_CONTRACT.md; исходный шаблон DB-04/05 и KNOWLEDGE_INGESTION.md рассмотрены для объяснения текущей очереди. Реальное определение функций в схеме `katona` требует read-only проверки.

## Решение Павла от 23.10.2026

**Ни при каких ошибках не запускать автоматическую повторную обработку одного документа.** После первой попытки система сообщает отправителю Telegram об успешной публикации либо о невозможности публикации с понятной причиной. Пользователь сам принимает решение, исправлять ли файл и присылать его снова; для нового запроса требуется новое Telegram-событие/загрузка. Это касается также временной ошибки OpenAI, PostgreSQL или сети: сообщить о технической проблеме и предложить попытаться позже вручную.

Очередь входящих событий и кратковременная асинхронная обработка могут сохраниться для надёжности приёма, но повторный запуск всего worker для одной загрузки запрещён. Отдельные попытки **доставки итогового Telegram-уведомления** не считаются повторной обработкой документа: уведомление имеет собственное независимое исходящее действие и учёт подтверждённой/неизвестной доставки. Обещать полное отсутствие дублей Telegram API нельзя.

## Фактическая проблема сейчас

1. Служебный Telegram Webhook работает, документ `Katona_adresa_grafik_kontakty.md` зарегистрирован, но не опубликован.
2. Несколько worker executions завершились `prepare_rezultat=povtor`, `kod_oshibki=dokument_zanyat`, `versiya_id=null` в `KB-01B2 Итог без возврата`. Это свидетельство конфликта занятости **логического документа**, а не ошибка его Markdown.
3. Пятиминутный Schedule Trigger Павел отключил и опубликовал изменение; Running executions в n8n нет. Однако новый входящий документ может сразу запускать worker через `KB-01A Запустить обработку знаний?`.
4. Живая схема `katona` ещё не исследована по заданиям; не утверждать, что конкретный lease завис или что причиной был неверный документ.

## Требуемые состояния и сообщения

| Результат попытки | Действие БД/worker | Итоговое сообщение Telegram |
| --- | --- | --- |
| Корректный документ, проверки и публикация прошли | Сохранить опубликованную версию атомарно, завершить задание | «Документ опубликован», название, версия |
| Ошибка UTF-8, YAML, структуры Markdown или обязательных полей | Терминально остановить конкретное задание, пометить ошибку, сохранить код и безопасное описание | «Документ не удалось опубликовать: [конкретная причина]; исправьте [действие] и отправьте снова» |
| Нет контрольных вопросов или проверочный поиск не пройден | Не публиковать; остановить попытку в `ozhidaet_proverki` / терминальном состоянии, без автоповтора | Объяснить, что требуется дополнить, предыдущую активную версию оставить доступной |
| OpenAI 429/5xx, сеть, Supabase недоступна | Не выполнять новую обработку автоматически; при возможности зафиксировать техническую ошибку | «Не удалось закончить обработку из-за временной технической ошибки. Повторите отправку позже» |
| Неопределённый результат записи или сбой worker | Не объявлять ни успех, ни «не опубликовано», пока read-only проверкой не выяснено состояние; запретить автоматический повтор обработки | «Статус публикации пока не подтверждён, требуется проверка»; после проверки — финальный отчёт |
| `dokument_zanyat` / конкурентное задание | Не подменять эту причину «ошибкой файла», не пересчитывать embeddings в цикле. Закончить попытку с видимым исходом и зафиксировать идентификатор блокировки; соблюдать lease/fencing | «Другой процесс уже обрабатывает этот документ. Автоматические повторы остановлены, проверьте статус» |
| Дубликат Telegram update | Вернуть уже записанное состояние того же события без повторной обработки | Понятный статус прежней попытки без ложного «опубликовано» |
| Ручная отмена | Завершить только выбранную непубликованную загрузку защищённой DB-операцией, заблокировав позднюю публикацию через fencing | «Загрузка отменена». Уже опубликованное не отменять этой операцией |

**Промежуточное подтверждение:** после сохранения bytes отправить «Файл принят, публикация ещё не завершена». Это не итоговый успех. **Финальное уведомление:** отдельно после подтверждённой публикации или документированного завершения с ошибкой.

## Дополнение Павла: не хранить неудачные файлы (23.10.2026)

Павел отдельно уточнил: после неудачной загрузки содержимое файла не должно оставаться в n8n/Supabase, а ошибка должна отправляться в Telegram. Это **новое требование к будущему хранилищу**. В текущем schema `katona` функция регистрирует файл заранее, а `zagruzki_znaniy.ishodnyy_fayl` обязательное `bytea NOT NULL`. Поэтому одна отмена задания не удалит bytes и не реализует новое правило.

Реализация потребует:
- временной staging-зоны с ограничением доступа и сроком хранения; успешная публикация переносит проверенную версию в постоянный контур;
- после неуспеха — удаление содержимого исходника из staging с контролируемым сроком очистки, при сохранении только минимального кода причины, ID и факта завершения;
- в n8n — ограничение сохранения execution-data/binary-data и проверка политик backups, logs и Telegram file storage (нельзя обещать мгновенное исчезновение из всех резервных копий);
- отдельной очереди/статуса итогового Telegram-уведомления, не инициирующей новую обработку;
- проверки, что ни один ошибочный/неутверждённый фрагмент не доступен клиентскому RAG.

**Текущая отмена:** Павел разрешил только терминально закрыть две конкретные тестовые загрузки. Удаление их оригинальных байтов, истории и всего документа НЕ разрешено и в SQL отмены не включено.

## Обязательные правила безопасности

- Supabase `katona` — источник истины. Отмена/терминальные переходы, lease, fencing и отказ от поздней публикации должны выполняться атомарно через разрешённые SECURITY DEFINER функции, а не прямым UPDATE под n8n-ролью.
- Нельзя просто выключить расписание и считать очередные задания отменёнными. Для «зависших» нужна диагностика и разрешённый безопасный переход состояния.
- Не показывать в Telegram исходные bytes документа, секреты и stack trace. Показывать нормализованную причину и одно предлагаемое действие пользователя. Если причина неизвестна, прямо указать, что диагностика ещё требуется.
- Отмена загрузки не удаляет данные и не отзывает ранее опубликованную активную версию. Исправленный файл — новая попытка с новым Telegram update, даже если logical ID документа прежний.
- При сбое отправки Telegram-уведомления нельзя заново публиковать документ; результат публикации и результат уведомления сохранять раздельно.
- Обычный пользователь видит статус своей загрузки. Команды отмены, если появятся (`/kb_status` и `/kb_cancel` — **только предложение**), проходят server-side авторизацию в рамках компании.
- Работающий служебный бот сохраняет другие функции; менять только ветки базы знаний. Не включать расписание до реализации нового решения и проверки текущего задания.

## KAT-KB-RETRY-01A — диагностика живой БД 23.10.2026

**Статус: выполнена проверка основного конфликта, без изменения данных.** Отчёт Supabase:
- По одному logical document имеются две загрузки одного имени; у одной версии документа сохранён ID, но `aktivnaya_versiya_id = null`. Публикация не подтверждена.
- Раннее задание: `v_rabote`, `popytki=1`, lease истёк до момента проверки. В n8n работающих Executions не было, по сообщению пользователя.
- Позднее задание: `povtor`, `popytki=3`, не владеет арендой, готово к следующему повтору при возвращении worker.
- Поэтому есть подтверждённый логический конфликт: запись в статусе `v_rabote` с истёкшим `arenda_do` может блокировать последующее задание. В исходном SQL шаблона проверка `dokument_zanyat` ищет другую запись `v_rabote` без проверки срока lease. **Соответствие перенесённой функции Катоны исходнику пока не подтверждено чтением её текущего определения.**
- Не установлена первопричина, почему раннее задание не завершилось (возможны сбой/неверный Credential/обрыв ветки и др.). Не утверждать, что Markdown некорректен.
- **Вторая read-only проверка завершена:** единственная версия №1 имеет статус `chernovik`, `vremya_proverki=null`, `vremya_publikacii=null`, активной версией не является. Обе загрузки имеют `status=obrabotka`; ранний job всё ещё `v_rabote` с истёкшей арендой, поздний — `povtor`. Следовательно, отменять можно только непубликованные попытки, но нельзя утверждать, что отмена уже выполнена.
- Следующая задача с отдельным разрешением — адресное прекращение обеих непубликованных загрузок, после повторной проверки тех же строк в транзакции и защиты от поздней публикации. По существующим ограничениям таблиц (из исходного SQL) предполагаемые конечные статусы: job `otmeneno`, upload `oshibka` с безопасным кодом отмены (поскольку у upload нет статуса `otmeneno`), версия `oshibka` или сохранённый неактивный черновик согласно проверенному актуальному контракту. **Это проект, не выполненный SQL; выбрать переход после чтения текущих функций/ограничений в `katona`.** Не менять активный указатель, не удалять исходник/фрагменты, не трогать другие компании.
- Для ручного отменяющего SQL подготовить транзакцию с конкретными ID, guard по двум job-status, expiry lease, draft status, `aktivnaya_versiya_id IS NULL`, независимостью от текущих n8n executions; при несовпадении условий — `ROLLBACK`. Перед исполнением запросить явное разрешение Павла на отмену именно этих двух тестовых заданий.

**Текущий безопасный режим:** пятиминутный Schedule Trigger отключён и опубликован пользователем. Другие worker-старты через регистрацию новых файлов возможны. Не загружать файлы повторно, не возобновлять расписание, не сбрасывать lease и не выполнять прямые изменения, пока не завершена проверка и не согласована адресная отмена.

## Подготовленный SQL для текущих двух TEST загрузок

23.10.2026 пользователь разрешил только их адресную отмену через SQL Editor. Подготовлен локально передаваемый в чате полный SQL `KATONA_KB_CANCEL_TWO_TEST_UPLOADS_GUARDED.sql`. Файл содержит реальные UUID текущих строк и поэтому **не загружается в публичный репозиторий**.

Транзакция проверяет активную версию NULL, единственный черновик, точные статусы двух заданий и загрузок, истёкшую аренду, отсутствие других активных заданий, наличие защитных status gates у SQL-функций, затем атомарно:
- переводит два job в `otmeneno` и очищает lease;
- переводит неактивный черновик в `oshibka` для блокирования отложенной публикации;
- закрывает обе upload в `oshibka` с явным кодом `otmena_adminom_test`, поскольку upload не имеет состояния `otmeneno`;
- не удаляет исходные bytes/архив/фрагменты/историю, не переключает активную версию и не затрагивает другую компанию.
При несовпадении условий — исключение и полный откат до COMMIT; после успешного COMMIT любое обратное изменение требует отдельной согласованной операции с повторной проверкой. **По состоянию документации SQL не выполнен; пользователь ещё не прислал результат.**
