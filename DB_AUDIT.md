# Аудит Supabase Qbit → Катона (21.10.2026)

Источник: выгрузка пользователя по SQL №1Б, схема `qbit_bot_pervichnogo_obrascheniya`. Это **метаданные структуры**, не сами данные и не тела функций.

## Подтверждено
- 35 обычных таблиц, 485 столбцов.
- 301 ограничение: 194 CHECK, 69 FOREIGN KEY, 35 PRIMARY KEY, 2 UNIQUE, 1 constraint-trigger.
- 135 индексов, включая `ix_fragmenty_hnsw_cos` (HNSW, cosine).
- 65 функций, все `SECURITY DEFINER`; 61 PL/pgSQL + 4 SQL.
- 5 пользовательских триггеров.
- 1 IDENTITY-последовательность (колонка `zagruzki_znaniy.poryadok_priema`).
- Расширения: `pgcrypto`, `uuid-ossp`, `vector` (0.8.2).
- Единственный фактический столбец с векторами: `fragmenty_znaniy.vektor vector(1024)`. Дополнительная запись вида `ix_fragmenty_hnsw_cos.vektor` в аудите — индекс, **не вторая таблица**.
- RLS на всех 35 таблицах исходника выключен.
- `row_estimate` — оценки PostgreSQL, не точные количества; у некоторых таблиц -1.

## Решения
- Создавать целевую схему `katona` только в **той же БД Supabase**, где есть исходник; при другом проекте нужен отдельный экспорт/импорт.
- Первый этап: только пустые таблицы, поля, PK/UNIQUE/CHECK, FK, индексы и IDENTITY. Не копировать пользователей, историю сообщений, идентификаторы каналов, Telegram менеджеров.
- Векторы Qbit не публиковать как знания Катоны. Создавать новые материалы Катоны и новые embedding-векторы после переноса функций.
- Тела 65 функций не были включены в SQL №1Б. Нужно отдельно получить `pg_get_functiondef`, проверить отсутствие старых ссылок на Qbit и подготовить безопасные роли/владельцев для `SECURITY DEFINER`.
- Вынести конфигурацию Telegram, OpenAI и профиля знаний из Qbit в значения Катоны.
